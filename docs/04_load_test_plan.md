# 負荷試験計画

## 目的

`scaling_levels` の各レベルの容量を**実測値**で確定する。
同梱の既定値(2 / 5 / 15 / 40)は形式を示すプレースホルダであり、
そのまま本番に使ってはならない。

---

## 前提の確認(試験前に埋める)

| 項目 | 値 | 出典 |
|---|---|---|
| 登録ID数 | | |
| 災害時の同時アクセス率 | | 過去の災害時アクセスログ、なければ想定 |
| 想定同時接続ユーザー数 | 登録ID数 × 同時アクセス率 | |
| 1ユーザーあたりのリクエスト数/分 | | 画面遷移の実測 |
| 想定ピークRPS | 同時ユーザー数 × リクエスト数 ÷ 60 | |
| 許容レスポンスタイム(p95) | | SLO |
| 許容エラー率 | | SLO |

**数万IDが一斉アクセス**する前提なら、例えば登録3万ID・同時アクセス率60%・
1人あたり6リクエスト/分 なら ピーク 1,800 RPS。この数字を起点にする。

---

## 禁止事項

- **本番環境での無承認の負荷試験を行わない**(SKILL.md 禁止事項)
- AWS への負荷試験は[簡易ネットワークストレステストポリシー](https://aws.amazon.com/jp/security/penetration-testing/)の範囲内で行う
- 本番DBに対する書き込み負荷試験は行わない

|---|---|---|---|

| Aurora インスタンスクラス / ACU範囲 | | | |

| データ量 | | | クエリ性能に直結。可能な限り本番相当にする |

## 試験1: 単一タスクの処理能力測定

**目的:** 1タスクあたりの限界RPSを求める。すべての容量計算の基礎になる。

| 手順 | 内容 |
|---|---|
| 1 | ECS `desiredCount = 1` に固定(Auto Scaling を一時的に無効化) |
| 2 | Aurora は十分な容量(最大ACU)に固定し、DBをボトルネックから外す |
| 3 | RPS を段階的に上げる(10 → 20 → 50 → 100 → …) |
| 4 | p95レスポンスタイムがSLOを超える直前のRPSを記録 |

**記録項目**

| RPS | p95 (ms) | エラー率 | CPU% | メモリ% |
|---|---|---|---|---|
| | | | | |

→ **1タスクあたりの安全RPS** = 限界RPS × 0.7(安全率)

---

## 試験2: 線形スケール性の確認

**目的:** タスクを増やした分だけ性能が上がるか確認する。上がらなければ
Web層以外にボトルネックがある。

| タスク数 | 期待RPS | 実測RPS | 線形性 | ボトルネック |
|---|---|---|---|---|
| 1 | | | 基準 | |
| 5 | | | | |
| 15 | | | | |
| 40 | | | | |

線形性が崩れた時点の要因を必ず特定する。

| 症状 | ボトルネック |
|---|---|
| `DatabaseConnections` が上限に張り付く | DB接続数 |
| `ServerlessDatabaseCapacity` が最大ACUに張り付く | DB容量 |
| ALB `TargetResponseTime` は低いのに全体が遅い | 認証基盤 / 外部API |
| ECS CPU に余裕があるのに遅い | ロック競合 / 共有リソース |

---

## 試験3: Aurora Serverless v2 の追随性測定

**目的:** 最小ACUを引き上げてから実際に容量が増えるまでの時間を測る。
これが事前スケールの「どれだけ前に実行すべきか」を決める。

| 手順 | 内容 |
|---|---|
| 1 | 最小ACU 0.5 の状態から `modify_db_cluster` で 16 に変更 |
| 2 | `ServerlessDatabaseCapacity` メトリクスが16に到達するまでの時間を計測 |
| 3 | 3回繰り返して平均を取る |

**記録:** 最小ACU引き上げ完了までの時間 = ______ 秒

---

## 試験4: 事前スケールの所要時間測定(最重要)

**目的:** 「気象庁の電文受信」から「実際に受け入れ可能になる」までの時間を測る。

```
電文受信 → 判定 → SFN起動 → Aurora変更 → MinCapacity変更
        → desiredCount変更 → タスク起動 → ALB healthy
```

| 区間 | 目標 | 実測 |
|---|---|---|
| 電文受信 → 判定完了 | < 5秒 | |
| 判定 → SFN起動 | < 5秒 | |
| Aurora 最小ACU反映 | < 60秒 | |
| desiredCount 変更 → 1タスク目 RUNNING | < 60秒 | |
| 全タスク ALB healthy | < 300秒 | |
| **合計(LEVEL_0 → LEVEL_3)** | **< 10分** | |

**判定基準:** 合計時間が10分を超える場合、警報発表から実災害までの時間差では
間に合わない可能性がある。イメージの軽量化、SOCIインデックスの導入、
`baseline_reserve_tasks` の引き上げを検討する。

**地震の場合:** 震度速報は地震発生から約1.5分で配信される。合計時間が
そのまま「サービスが苦しい時間」になるため、常時予備容量の設計に直結する。

---

## 試験5: ピーク負荷試験

**目的:** LEVEL_3 の容量で想定ピークRPSを捌けることを確認する。

| 手順 | 内容 |
|---|---|
| 1 | 手動強制拡張で LEVEL_3 にする |
| 2 | 全タスクが healthy になるまで待つ |
| 3 | 想定ピークRPSで10分間の定常負荷をかける |
| 4 | さらに 1.5倍 のRPSで5分間かける(余裕度の確認) |

**合格基準**

- p95レスポンスタイム ≤ SLO
- エラー率 ≤ SLO
- Aurora の接続数が最大接続数の80%以下
- ECS CPU 使用率が70%以下

---

## 試験6: 急峻な立ち上がり試験

**目的:** 実際の災害では負荷が段階的ではなく一気に立ち上がる。

| 手順 | 内容 |
|---|---|
| 1 | LEVEL_0(平時容量)から開始 |
| 2 | 事前スケールを実行 |
| 3 | 拡張完了の**2分後**にピークRPSを一気に投入(ランプアップなし) |
| 4 | エラー率とレスポンスタイムを記録 |

事前スケールなしのケース(LEVEL_0 のまま一気に投入)とも比較し、
事前スケールの効果を定量化する。

---

## 試験7: 段階縮小試験

**目的:** 縮小中にリクエストが落ちないことを確認する。

| 手順 | 内容 |
|---|---|
| 1 | LEVEL_3 で定常負荷(ピークの30%)をかけ続ける |
| 2 | 段階縮小を実行(5タスクずつ) |
| 3 | 各段階でエラーが発生しないことを確認 |

ECSのデプロイ設定(`deregistration_delay`、`minimumHealthyPercent`)が
適切であればエラーは出ないはず。出る場合は既存サービス側の設定見直しが必要
(**既存システムの変更にあたるため、実施可否を要確認**)。

---

## 試験8: 復旧試験

| ケース | 手順 | 期待結果 |
|---|---|---|
| 監視Lambda停止からの復旧 | スケジューラを無効化 → 15分後に有効化 | アラーム発報 → 復旧後に正常判定 |
| Step Functions 失敗からの復旧 | IAM権限を一時的に剥奪 → 拡張を実行 → 権限を戻して再実行 | 容量が縮小しない / 再実行が冪等 |
| DynamoDB 障害 | テーブルへのアクセスを一時的に拒否 | ロック取得失敗でスキップ、容量は変化なし |
| Aurora フェイルオーバー | フェイルオーバーを実行 | 拡張処理が失敗しても Web層の容量は維持 |

---

## 試験結果の反映

試験完了後、以下を確定して `terraform.tfvars` に反映する。

```hcl
scaling_levels = {
  level_0 = { ecs_desired_count = ?, ecs_min_capacity = ?, aurora_min_acu = ?, aurora_max_acu = ? }
  level_1 = { ... }   # 想定ピークの 10-15%
  level_2 = { ... }   # 想定ピークの 40-50%
  level_3 = { ... }   # 想定ピークの 100% + 余裕20%
}

absolute_max_ecs_tasks = ?   # level_3 の 1.25倍程度
baseline_reserve_tasks = ?   # 地震発生から拡張完了までを耐えられる最小台数
```

**`baseline_reserve_tasks` の決め方:**
試験4で測った「拡張完了までの合計時間」の間に到達するリクエストを
エラーにせず捌ける台数。地震のように予兆がない災害への唯一の備えになる。
